telegram-api :8080 (Process)

Description: Receives Telegram messages, publishes events, interacts with Redis, users, web-admin and Vault for secrets

Number
Title
Type
Severity
Status
Score
Description
Mitigations
Telegram token compromiseSpoofingHighOpenCompromise of TELEGRAM_TOKEN allows interaction with Telegram Bot API on behalf of the bot.Store TELEGRAM_TOKEN in Vault with least-privilege policy, restrict Vault access, do not log secret values, rotate token.
Unauthenticated internal service callsInformation disclosureHighOpenInternal HTTP calls from telegram-api to users, web-admin, Redis and Kafka may lack mTLS or service authentication.Add mTLS or internal service authentication; restrict with NetworkPolicy.
Telegram message floodDenial of serviceMediumOpenMissing rate limiting on incoming Telegram messages can overload telegram-api, Redis, Kafka and users.Rate limit by chat_id/user_id, add backpressure, resource limits and autoscaling.

scheduler (Process)

Description: Background scheduler interacting with Redis, users and Vault for TELEGRAM_TOKEN

Number
Title
Type
Severity
Status
Score
Description
Mitigations
Redis pub/sub tamperingTamperingHighOpenScheduler reads or publishes Redis pub/sub without confirmed authentication.Enable Redis ACL/password, restrict NetworkPolicy, sign critical messages.
Scheduler token disclosureInformation disclosureMediumOpenAny pod with access to Secret or environment may read TELEGRAM_TOKEN.Restrict Vault policy and service account access, do not log env, rotate tokens and revoke leaked Vault tokens.

recommender :8080 (Process)

Description: Generates recommendations using Redis, users, analytics, OpenRouter and Vault for OPENROUTER_API_KEY

Number
Title
Type
Severity
Status
Score
Description
Mitigations
OpenRouter key compromiseSpoofingHighOpenCompromise of OPENROUTER_API_KEY allows use of project LLM quota or funds.Store key in Vault, restrict access by service account, rotate key, configure provider budget and quotas.
User data sent to external LLMInformation disclosureHighOpenRecommender sends user data to external OpenRouter API.Anonymize chat_id/user_id, remove PII from prompt, configure retention with provider.
LLM latency blocks recommendationsDenial of serviceMediumOpenOpenRouter or LLM latency can block recommendation processing.Use rate limiter, max concurrency, circuit breaker, timeout and queue backpressure.

web-admin :8080 (Process)

Description: Web administration UI exposed through admin.sparktonapp.ru, uses Vault for SESSION_KEY

Number
Title
Type
Severity
Status
Score
Description
Mitigations
Admin session spoofingSpoofingMediumOpenCompromise of SESSION_KEY can allow forged admin sessions.Store SESSION_KEY in Vault, rotate it, use HTTPOnly, Secure, SameSite cookies and short TTL.
Admin UI exposed to InternetInformation disclosureMediumOpenIngress admin.sparktonapp.ru exposes web-admin to the Internet.Keep TLS, add HSTS, rate limiting, authentication and audit logging.
Cross-user data accessElevation of PrivilegeHighOpenweb-admin may read analytics or users data without proper authorization checks.Authorize by chat_id/user_id and do not rely only on client-side checks.

users :8080 (Process)

Description: User service, PostgreSQL-backed user data and Vault for database credentials

Number
Title
Type
Severity
Status
Score
Description
Mitigations
Unauthenticated users APISpoofingHighOpenusers API is available inside the cluster without confirmed caller authentication.Add internal service authentication or mTLS; restrict callers with NetworkPolicy.
Unauthorized CRUD callsTamperingHighOpenAny service in dev namespace may call users CRUD endpoints.Authorize by caller identity, use RBAC/NetworkPolicy and block unnecessary direct access.
PostgreSQL emptyDir data lossDenial of serviceHighOpenusers depends on PostgreSQL on emptyDir and can lose data when pod is recreated.Use PersistentVolumeClaim, backup/restore and readiness/liveness probes.

analytics :8080 (Process)

Description: Consumes Kafka events and writes analytics to ClickHouse

Number
Title
Type
Severity
Status
Score
Description
Mitigations
Unverified Kafka event processingSpoofingHighOpenKafka consumer may process unverified events from answers.received.Use Kafka TLS listener 9093, ACLs/SASL and verify producer identity.
Metrics endpoint disclosureInformation disclosureMediumOpen/metrics is available without authentication and can reveal internal information.Restrict /metrics with NetworkPolicy, add metrics auth and avoid PII in metrics.
Excessive analytics accessElevation of PrivilegeMediumOpenanalytics may read or aggregate user data it should not access.Authorize at API level and minimize PII in Kafka and ClickHouse.

Kafka Cluster (Process)

Description: Kafka broker cluster in namespace kafka

Number
Title
Type
Severity
Status
Score
Description
Mitigations
Kafka plaintext listenerInformation disclosureHighOpenKafka has plaintext listener 9092 with tls=false.Use TLS listener 9093, disable plaintext listener and enable SASL/ACL.
Kafka topic tamperingTamperingHighOpenWithout ACL any authorized producer/consumer can write or read answers.received.Use Kafka ACLs, separate service accounts and restrict dev access.
Kafka availability weaknessDenial of serviceHighOpenKafka replication factor and min.insync.replicas are set to 1.Increase replication factor and min ISR for production and monitor lag.

Number
Title
Type
Severity
Status
Score
Description
Mitigations

Description: User database store

Number
Title
Type
Severity
Status
Score
Description
Mitigations
Postgres secret exposureInformation disclosureMediumOpenPOSTGRES_PASSWORD is stored in Vault; broad Vault policies or compromised users service can expose it.Restrict Vault policy to users service, use short-lived credentials where possible and rotate credentials.
PostgreSQL data lossDenial of serviceHighOpenPostgreSQL uses emptyDir and can lose data when pod is recreated.Use PVC, backup/restore and monitor disk.

Number
Title

Score
Description
Mitigations
Redis pub/sub tamperingTamperingHighOpenRedis pub/sub may be available to any pod inside namespace without ACL/password authentication.Enable Redis ACL/password, separate users/channels and restrict NetworkPolicy.
Redis user data disclosureInformation disclosureMediumOpenRedis may store temporary user data, sessions or last recommendations.Do not store PII longer than necessary, enable auth and restrict access.

ClickHouse :9000 (Store)

Description: Analytics data store

Number
Title
Type
Severity
Status
Score
Description
Mitigations
ClickHouse unauthenticated accessInformation disclosureHighOpenClickHouse manifests create no TLS certs and accessManagement is false.Enable TLS, access management, separate users/roles and restrict NetworkPolicy.
Analytics data tamperingTamperingMediumOpenA user with ClickHouse access may modify analytical data.Use RBAC/roles, audit, backups and readonly analytics roles.

Vault :8200 (Store)

Description: Central secret store for service credentials and API keys

Number
Title
Type
Severity
Status
Score
Description
Mitigations
Vault policy bypassElevation of PrivilegeHighOpenOverly broad Vault policies or Kubernetes service account bindings may let a service read secrets it does not need.Use least-privilege Vault policies, bind secrets to service accounts, audit secret reads and rotate exposed credentials.
Vault token leakageInformation disclosureHighOpenVault tokens or AppRole responses may be exposed through environment variables, logs or pod compromise.Use short TTL tokens, avoid logging Vault responses, inject secrets only into required pods and revoke leaked tokens.
Vault availability dependencyDenial of serviceMediumOpenServices that fetch secrets at startup may fail if Vault is unavailable.Run Vault highly available, cache only necessary secrets with TTL, add readiness checks and secret-refresh fallback.
